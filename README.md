# GSB Bugfix Task
## 题面
邮箱验证口令上线后，客服和安全各执一词：有人收不到信，有人发现口令能被脚本猜开。生成器用了可预测的种子，同一个信箱连发三次居然是同一串；库里直接存明文，后台一导出全泄露；口令十分钟不失效，隔天还能提交；错误次数不封顶，脚本可以一直猜；补发没有冷却，一秒点十下把邮件网关打满；补发之后旧口令还活着，两封信里的都能过；信箱首尾空格和大小写让口令对不上；输入里夹空格被判格式错却不计失败次数；口令用掉一次还能再用；未知信箱直接抛内部异常，泄露存储结构；吊销只删了最近一条；快照里能翻到盐值和明文。email_otp_service.py 的 EmailOtpService 负责发放与核验：口令六位数字、随机源足够强、落库只留摘要；发放前规范化信箱，补发设冷却且新口令即时顶掉旧的，旧口令再提交按已被替换处理；有效期内只认一次核验；错误累计到上限就封锁，封锁后正确口令也拒；格式非法按参数错误处理；未知信箱、已核验、已过期各报各的错误码；发放返回的明文仅供投递，库存与快照只留摘要；比较用固定时间算法，长度不同也不提前返回；同一信箱只保留一条挑战，补发覆盖不追加；封锁状态发放接口也要识别，封锁期间不得再发；吊销后旧挑战连同失败计数一起清掉；挑战记录要带创建时刻与失败计数，成功核验后整条删除；补发时先查封锁状态再查冷却；不同信箱之间互不影响；快照里的摘要不能反推出六位口令；快照是副本。十五条断言目前全红，测试不许动。

## 运行方式
```bash
python -m pytest tests -q
```
